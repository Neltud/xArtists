0. RÉSUMÉ EXÉCUTIF (pour auditeur externe)
--------------------------------------------------------------------------------
xArtists est une dApp MultiversX combinant :
  - Galerie / Studio NFT (art phygital + digital)
  - Marketplace NFT + marketplace d’agents IA (packs LIA)
  - Token $TRO (TRO-94c925, plafond produit 500 000)
  - Agent de trading autonome LIA (paper-first, gates fail-closed)
  - Intégrations DeFi (Hatom, xExchange, Burnify protocole, etc.)
  - Fondation / treasury (fees, tips, PnL LIA) — policy documentée

POSTURE DE RISQUE ACTUELLE (honnête) :
  * Trading LIA LIVE = DÉSACTIVÉ (LIA_LIVE_TRADING=0)
  * Marketplace NFT adresse présente MAIS codeHash NULL (compte vide)
  * agents_marketplace = NULL (jamais déployé)
  * tro_burn (SC xArtists) = NULL (code prêt, non déployé)
  * Micro-preuves on-chain réussies = 0
  * go_live_gates : all_critical_ok=false, allow_live_trading=false

VERDICT PRODUIT : code et UX largement « private release / pre-mainnet ».
  Les modules qui collecteraient de l’argent utilisateur on-chain (Buy NFT,
  Buy agent, Vote TX, Burnify user SC) sont volontairement bloqués ou
  bandeaux « SC non déployé ». C’est la bonne posture tant que les SC ne
  sont pas live avec codeHash vérifié.

  e2e/               Playwright

1.2 Flux utilisateur (haut niveau)
  Visiteur → GH Pages SPA
    → Connect wallet (xPortal / Web / extension) ≠ wallet LIA protocole
    → Studio (mint/metadata IPFS Pinata) / Gallery / Marketplace
    → Agents (packs LIA vs GreenSmoke forecasts — séparés)
    → Trading / Portfolio = vues LIA paper + oracles (pas le portefeuille user)
    → DAO lecture ($TRO) ; vote on-chain non garanti sans SC/sdk complet
    → Tip / Ads / Editions (contenu + monétisation soft)

1.3 Flux LIA (ops)
  Timer Vellum → perception (oracles, social, board)
    → décision (modes DEFENSE/COMPOUND/MICRO_ARB/…)
    → Guardian (VaR/Kelly/preflight)
    → Executor (paper par défaut)
    → publish JSON → Pages
  Burnify protocol path : stake BFY → batches TRO → claim EGLD après X batches
  (module lia/burnify/, wallet LIA uniquement)

1.4 Séparation des rôles d’argent (critique sécurité produit)
  LIA Ops (erd1p4zyy…lerqu0crn6)  = exécution protocole, balances Dashboard « protocole »
  User Connect                      = tips, buys — JAMAIS le wallet LIA en session user
  Fee Collector SC                  = après deploy market/agents (claimFees owner)
  Mission / Reserve                 = policy treasury (adresses à créer / multisig)

12. CONCLUSION SÉCURITÉ
--------------------------------------------------------------------------------
Le projet montre une maturité documentaire et des gates paper/fail-closed
solides pour un stade pre-TVL. Les risques majeurs ne sont plus « code absent »
mais :
  (1) déploiement SC et vérification codeHash avant d’ouvrir le cash user ;
  (2) concentration owner LIA single-key ;
  (3) dette Mission/Reserve non matérialisée ;
  (4) confusion possible user si bandeaux retirés trop tôt ;
  (5) surface multichain (HL/Solana) si flags live activés sans discipline.

Recommandation : traiter P0 deploy + verify + multisig treasury AVANT tout
LIA_LIVE_TRADING=1 et avant tout marketing « marketplace live ».
