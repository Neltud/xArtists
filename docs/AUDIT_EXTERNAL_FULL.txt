0. RÉSUMÉ EXÉCUTIF
--------------------------------------------------------------------------------
xArtists est une dApp MultiversX combinant art NFT (phygital/digital), marketplace,
packs d'agents IA LIA, token $TRO (plafond produit 500 000), agent de trading
autonome LIA (paper-first), DeFi (Hatom, xExchange, Burnify), et une treasury de
fondation décentralisée (fees + tips + PnL LIA discipliné).

POSTURE DE RISQUE (snapshot gates 2026-08-11) :
  LIA_LIVE_TRADING                 = 0
  allow_live_trading               = false
  all_critical_ok                  = false
  marketplace codeHash             = NULL (compte vide)
  agents_marketplace               = null
  treasury_splitter / tro_burn /
    rwa_escrow_bridge              = null (code source prêt)
  micro_proofs réussis             = 0
  PEM in repo                      = clean

VERDICT : private release / pre-mainnet honnête. Le front refuse d'ouvrir le cash
utilisateur tant que les SC critiques n'ont pas de codeHash vérifié. C'est la
bonne posture. Le goulet n'est plus le code applicatif : c'est le déploiement
mainnet + wallets Mission/Reserve + multisig owner.

9. MEILLEURES PRATIQUES — RECOMMANDATIONS
--------------------------------------------------------------------------------
9.1 Smart contracts
  • CEI systématique (déjà sur market / escrow / splitter) — conserver
  • Pause + 2-step ownership sur tout SC à TVL
  • Owner = multisig dès que Mission/Reserve existent
  • claimFees → receiveAndSplit en procédure ops datée ≤ 7 j
  • Tests blackbox obligatoires avant marketing « live »
  • codeHash publié dans data/contracts.json + UI ScStatusBanner
  • Pas d'upgrade sans policy écrite (qui signe, délai, annonce)

9.2 Frontend
  • Fail closed : pas de Buy si codeHash null (déjà)
  • Jamais de session user = LIA Ops (déjà)
  • Labels « protocole » vs « mon wallet » partout
  • Lazy MxDappProvider seulement pages TX
  • Virtualisation catalogue > 500 (VirtualNftGrid)
  • Lighthouse CI post-rebuild
  • Une seule source UI : apps/frontend

9.3 LIA / Vellum
  • Paper-first ; micro-proofs ≥ 1 avant LIVE
  • Caps bridge et micro-trades (gas + notional)
  • Secrets uniquement Vellum / GH Actions — jamais git
  • Modes DEFENSE prioritaires sur profit
  • Journal paper + allocator pour améliorer modèles sans risque
  • Séparer packs vendus / GSN forecasts / wallet LIA

9.4 Treasury
  • Publier adresses Mission/Reserve même à 0
  • Rapport hebdo soldes ; mensuel PnL paper vs live séparés
  • Pas de promesse de performance aux utilisateurs
  • Tips ≠ investissement (copy claire)

9.5 Ops / release
  • Runbook deploy ligne par ligne (docs/RUNBOOK_*)
  • verify_marketplace_codehash avant tout VITE_* market
  • Private release strip jusqu'à codeHash OK
  • Incident : perte > seuil Reserve → post-mortem public

13. CONCLUSION
--------------------------------------------------------------------------------
Le projet présente une maturité documentaire et des contrôles paper/fail-closed
solides pour un stade pre-TVL. Les risques majeurs ne sont plus « absence de
code » mais :

  (1) Déploiement SC + vérification codeHash avant cash utilisateur
  (2) Concentration owner LIA single-key
  (3) Dette Mission / Reserve non matérialisée
  (4) Confusion possible si bandeaux retirés trop tôt
  (5) Surface multichain (HL / Solana / bridge) si flags live sans discipline
  (6) Dualité frontend legacy vs SPA Vite

Recommandation : enchaîner P0 wallets Mission/Reserve → deploy market/agents →
verify codeHash → post_deploy → micro-TX user → seulement alors envisager
LIA_LIVE_TRADING=1 et deploy splitter. Aucun marketing « marketplace live »
avant codeHash non-null.
